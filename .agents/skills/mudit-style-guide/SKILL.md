# Enterprise Front-End Development Style Guide

This document defines the strict coding conventions, architectural boundaries, and syntax rules for this repository. All code generated by AI agents or written by human contributors must adhere to these standards.

---

## 1. Core Architectural Philosophy

1. **Server-First Architecture:** Treat components as React Server Components (RSC) by default. Push interactive boundaries ("Use Client") to the leaves of the component tree.
2. **Explicit Type Safety over Boilerplate:** Use TypeScript’s inference wherever possible. Avoid redundant annotations that break framework features (e.g., async server components).
3. **Zero Legacy Patterns:** Strictly forbid deprecated or legacy React patterns (`React.FC`, `forwardRef`, `npm exec`).

---

## 2. React 19 & TypeScript Conventions

### Component Declarations & Props Typing
* **Do NOT use `React.FC` or `React.FunctionComponent`.**
* Type props directly on the function parameter using inline destructured object types or a standalone interface.
* Use standard `function` declarations for top-level components to support function hoisting and cleaner stack traces.

```tsx
// ✅ PREFERRED: Direct Parameter Props Typing with function declaration
interface ButtonProps {
  variant?: 'primary' | 'secondary';
  children: React.ReactNode;
  onClick?: () => void;
}

export function Button({ variant = 'primary', children, onClick }: ButtonProps) {
  return (
    <button className={`btn-${variant}`} onClick={onClick}>
      {children}
    </button>
  );
}

// ❌ BANNED: React.FC wrapper
export const Button: React.FC<ButtonProps> = ({ variant, children }) => { ... };
```

### Component Return Types
* **Omit explicit return type annotations (`: React.ReactNode` or `: JSX.Element`)** on component functions. Allow TypeScript to infer the return type automatically.
* *Reason:* Explicitly typing `: React.ReactNode` breaks `async` React Server Components, which return a `Promise<React.ReactNode>`.

```tsx
// ✅ PREFERRED: Inferred return type (works for both sync and async RSC)
export async function UserProfile({ userId }: { userId: string }) {
  const user = await fetchUser(userId);
  return <div>{user.name}</div>;
}

// ❌ BANNED: Explicit return type on components
export function UserProfile({ userId }: { userId: string }): React.ReactNode {
  return <div>...</div>;
}
```

### Native `ref` Passing (React 19)
* **Do NOT use `React.forwardRef`.** In React 19, `ref` is a standard prop that can be destructured directly from the props object.

```tsx
// ✅ PREFERRED: React 19 native ref prop
import { Ref } from 'react';

interface CustomInputProps {
  label: string;
  ref?: Ref<HTMLInputElement>;
}

export function CustomInput({ label, ref, ...props }: CustomInputProps) {
  return (
    <label>
      {label}
      <input ref={ref} {...props} />
    </label>
  );
}

// ❌ BANNED: React.forwardRef wrapper
export const CustomInput = forwardRef<HTMLInputElement, CustomInputProps>((props, ref) => { ... });
```

### Event Handler Typing
Use explicit event types from `React` when passing handlers separately from JSX:

```tsx
// ✅ PREFERRED: Explicit event typing for handler functions
function Form() {
  const handleChange = (e: React.ChangeEvent<HTMLInputElement>) => {
    console.log(e.target.value);
  };

  const handleSubmit = (e: React.FormEvent<HTMLFormElement>) => {
    e.preventDefault();
  };

  return (
    <form onSubmit={handleSubmit}>
      <input onChange={handleChange} />
    </form>
  );
}
```

## 3. Next.js App Router & Server Components

### Layout Contracts
Root layouts (`app/layout.tsx`) must export a default `RootLayout` component accepting destructured `children` wrapped in TypeScript's `Readonly<>` utility.

```tsx
// ✅ PREFERRED: Standard Next.js Root Layout
export default function RootLayout({
  children,
}: Readonly<{
  children: React.ReactNode;
}>) {
  return (
    <html lang="en">
      <body>{children}</body>
    </html>
  );
}
```

### Server vs. Client Component Boundaries
* **Default to Server Components:** Every component in `app/` is a Server Component unless explicitly marked with `"use client"`.
* **Placement of `"use client"`:** Place the directive at the very top of the file, above imports. Keep Client Components isolated to small interactive widgets (e.g., a single toggle button or modal trigger) rather than entire page trees.
* **Passing Data:** Pass serializable data from Server Components to Client Components. Never pass functions or non-serializable objects across the server/client boundary.

## 4. Hook Usage Guidelines (`useRef` vs. `useState`)

| Scenario | Tool to Use | Syntax Pattern |
| :--- | :--- | :--- |
| **Value updates trigger UI re-render** | `useState` | `const [val, setVal] = useState(initial);` |
| **Direct DOM node manipulation / measurement** | `useRef` | `const nodeRef = useRef<HTMLDivElement>(null);` |
| **Storing mutable background state (timers, IDs)** | `useRef` | `const timerId = useRef<NodeJS.Timeout \| null>(null);` |
| **Immediate callback execution on DOM mount** | Callback Ref | `const ref = useCallback((node: HTMLDivElement \| null) => { ... }, []);` |

### Rules for `useRef`
1. Never read or mutate `ref.current` directly in the component's render body.
2. Perform all ref reads and mutations inside event handlers or `useEffect` hooks.

## 5. Package Management & Build Engine Rules

### Package Manager Discipline (`pnpm`)
* **Default Manager:** `pnpm` is the sole allowed package manager for this repository.
* **Executing Package Binaries:**
  * Use `pnpm dlx` to download and execute one-off global CLI utilities (e.g., `pnpm dlx shadcn@latest add button`).
  * Use `pnpm exec` *only* for tools already installed in `node_modules` (e.g., `pnpm exec tsc --noEmit`).
  * Never use `npm exec`, `npx`, or `yarn`.

### Build & Compilation Lifecycle
* **Dev Server:** Driven by **Turbopack** (`next dev --turbo`).
* **Transpilation:** Executed by **SWC** inside Rust.
* **Type Checking:** Decoupled from bundling. Run `tsc --noEmit` as a standalone check in CI pipelines or pre-commit hooks to verify type validity without blocking rapid local dev iterations.

## 6. Anti-Pattern Matrix

| Anti-Pattern | Why It Is Forbidden | Modern Correct Standard |
| :--- | :--- | :--- |
| `const Comp: React.FC<Props> = ...` | Legacy, implicit children bugs, RSC incompatible | `export function Comp({ prop }: Props)` |
| `export const Input = forwardRef(...)` | Deprecated in React 19 | Pass `ref` as a standard prop parameter |
| `function Page(): React.ReactNode` | Breaks `async` Server Components | Omit return type annotation; rely on TS inference |
| `npx <command>` / `npm exec` | Ignores repo lockfile consistency | Use `pnpm dlx <command>` |
| `useRef` mutation in render body | Causes race conditions & inconsistent render behavior | Mutate `ref.current` only inside effects or handlers |
| `"use client"` on top-level pages | Disables React Server Component streaming & bundle splitting | Keep pages as RSC; extract interactive elements to leaf client components |

## 7. Type Validation with Zod

You are an expert TypeScript developer who understands that type assertions (using `as`) only provide compile-time safety without runtime validation.

## Zod Over Type Assertions

- **NEVER** use type assertions (with `as`) for external data sources, API responses, or user inputs
- **ALWAYS** use Zod schemas to validate and parse data from external sources
- Implement proper error handling for validation failures

## Zod Implementation Patterns

- Import zod with: `import { z } from 'zod'`
- Define schemas near related types or in dedicated schema files
- Use `schema.parse()` for throwing validation behavior
- Use `schema.safeParse()` for non-throwing validation with detailed errors
- Add meaningful error messages with `.refine()` and `.superRefine()`
- Set up default values with `.default()` when appropriate
- Use transformations with `.transform()` to convert data formats
- Always handle potential validation errors 

```tsx
// ❌ WRONG: Using type assertions
interface User {
  id: string;
  name: string;
  email: string;
  age: number;
}

const fetchUser = async (id: string): Promise<User> => {
  const response = await fetch(`/api/users/${id}`);
  const data = await response.json();
  return data as User; // DANGEROUS: No runtime validation!
};
```
```tsx
//  RIGHT: Using Zod for validation
import { z } from 'zod';

// Define the schema
const UserSchema = z.object({
  id: z.string().uuid(),
  name: z.string().min(1),
  email: z.string().email(),
  age: z.number().int().positive().min(13),
});

// Derive the type from the schema
type User = z.infer<typeof UserSchema>;

const fetchUser = async (id: string): Promise<User> => {
  const response = await fetch(`/api/users/${id}`);
  const data = await response.json();

  // Runtime validation
  return UserSchema.parse(data);
};

// With error handling
const fetchUserSafe = async (id: string): Promise<User | null> => {
  try {
    const response = await fetch(`/api/users/${id}`);
    const data = await response.json();

    const result = UserSchema.safeParse(data);
    if (!result.success) {
      console.error('Invalid user data:', result.error.format());
      return null;
    }

    return result.data;
  } catch (error) {
    console.error('Error fetching user:', error);
    return null;
  }
};
```
